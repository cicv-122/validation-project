## ЗАДАЧА: ДЕКОМПОЗИЦИЯ КОМПОНЕНТА [ВСТАВЬ ИМЯ ФАЙЛА] Правила декомпозиции (обязательны): 1. ПОРОГ РАЗМЕРА - Компонент > 300 строк → обязательно декомпозировать - Один компонент = одна ответственность (Single Responsibility) - Хук > 80 строк → выносить в отдельный файл use*.ts 2. ВЫНОСИ В КАСТОМНЫЙ ХУК ЕСЛИ - Есть 3+ useState связанных с одной сущностью → useEntityName() - Есть useEffect с fetch-логикой → заменить на TanStack Query хук - Есть сложная логика фильтров/сортировки → useFilters() - Есть обработка форм → useForm() или react-hook-form 3. ВЫНОСИ В ОТДЕЛЬНЫЙ КОМПОНЕНТ ЕСЛИ - Блок > 50 строк JSX с собственным смыслом - Элемент повторяется 2+ раза - У блока есть собственное локальное состояние 4. ЗАПРЕЩЕНО - Менять props-интерфейсы компонентов (нет тестов, нельзя ломать) - Менять URL-пути и вызовы API - Переносить бизнес-логику бэкенда - Менять поведение — только структура 5. АЛГОРИТМ ДЕКОМПОЗИЦИИ Шаг 1: Прочитай весь файл и выпиши все useState — сгруппируй по домену Шаг 2: Определи все fetch/axios вызовы → замени на useQuery/useMutation Шаг 3: Выдели визуальные блоки JSX → создай именованные компоненты Шаг 4: Создай index.ts с публичными экспортами Шаг 5: Убедись что TypeScript types явно прописаны (no implicit any) Результат: список файлов которые нужно создать с кратким описанием каждого.

## ЗАДАЧА: SERVICE LAYER ДЛЯ DJANGO DRF ВАЖНО: URL-маршруты не меняются. Рефакторинг только внутри. ЦЕЛЕВАЯ СТРУКТУРА каждого Django-приложения apps/certification/ ├── api/ │ ├── views.py # только HTTP: get request → call service → return response │ ├── serializers/ │ │ ├── input.py # сериализаторы для записи (валидация входных данных) │ │ └── output.py # сериализаторы для чтения (представление данных) │ └── urls.py # маршруты — не трогаем ├── services.py # бизнес-логика (create_assessment, approve_candidate...) ├── selectors.py # запросы к БД (get_candidates_by_filter, get_dossier...) ├── models.py └── admin.py ПРАВИЛА РЕФАКТОРИНГА 1. views.py должен содержать только: - Получение данных из request - Вызов одного сервиса или селектора - Возврат Response 2. services.py — бизнес-логика: - Принимает plain Python объекты (не request, не queryset) - Возвращает plain Python объекты или model instance - Содержит транзакции (@transaction.atomic) - Выбрасывает доменные исключения (ValidationError, PermissionDenied) 3. selectors.py — запросы к БД: - Только select/filter/annotate — никаких изменений данных - Принимает параметры фильтрации - Возвращает QuerySet или конкретные значения 4. serializers/input.py — валидация входных данных: - Вынеси общую логику (например, валидация 14-значного ПИН КР) - Используй validate_ методы 5. Telegram-бот и фоновые команды: - Команды типа `python manage.py run_telegram_bot` и `services/telegram.py` обязаны использовать новые `selectors.py` и `services.py` - Сигнатуры поиска по ИНН/ФИО и выдачи статистики должны оставаться строго обратно совместимыми ПРИМЕР РЕФАКТОРИНГА # ДО: Fat View class AssessmentView(APIView): def post(self, request): pin = request.data.get('pin') if len(pin) != 14 or not pin.isdigit(): return Response({'error': '...'}, 400) candidate = Candidate.objects.filter(pin=pin).first() if not candidate: candidate = Candidate.objects.create(pin=pin, ...) assessment = Assessment.objects.create(candidate=candidate, ...) # ... 50 строк логики return Response(AssessmentSerializer(assessment).data) # ПОСЛЕ: Thin View class AssessmentView(APIView): def post(self, request): serializer = CreateAssessmentInputSerializer(data=request.data) serializer.is_valid(raise_exception=True) assessment = assessment_service.create_assessment( validated_data=serializer.validated_data, created_by=request.user, ) return Response(AssessmentOutputSerializer(assessment).data, 201) Type hints обязательны везде: def create_assessment(data: dict, user: User) -> Assessment

## ПРАВИЛА РЕФАКТОРИНГА ЧТО НЕЛЬЗЯ МЕНЯТЬ (поведение) - URL-маршруты и эндпоинты API (на них завязаны мобильные, QR-коды, Telegram-бот) - Props-интерфейсы компонентов, которые используются в других местах (нет тестов → нельзя рисковать) - Пользовательские сценарии: если раньше кнопка делала X, после рефакторинга она делает X - Форматы данных в запросах/ответах (JSON-контракты с бэком) - Маршруты React Router (пути страниц) - Синхронизацию параметров фильтрации и пагинации с URL (?tab=registry&page=...&target=...) - Официальные наименования ведомств: только «Министерство просвещения Кыргызской Республики (МП КР)» / «Кыргыз Республикасынын Агартуу министрлиги» - Работу Telegram-бота и фоновых демонов бэкенда ЧТО НУЖНО ПЕРЕПИСАТЬ (реализация) - useState × 15 → сгруппировать в кастомные хуки или Zustand-стор - useEffect + fetch/axios → заменить на useQuery/useMutation (TanStack Query v5) - Монолитный JSX → декомпозировать на именованные компоненты по ответственности - Fat Views (Django) → вынести логику в services.py + selectors.py - Дублирующаяся валидация → общие валидаторы в shared/ (например, validateKyrgyzPin()) - implicit any → явные TypeScript-типы и Zod-схемы - Ручные флаги loading/error → isLoading, isError из useQuery АЛГОРИТМ БЕЗОПАСНОГО РЕФАКТОРИНГА Шаг 1: git checkout -b refactor/feature-name ← всегда в отдельной ветке Шаг 2: Сделай изменение в одном файле Шаг 3: npm run build ← убедись что TypeScript не ругается Шаг 4: Вручную проверь пользовательский сценарий в браузере Шаг 5: Коммит → следующий файл КРИТЕРИЙ «ГОТОВО» Файл отрефакторен корректно если: ✓ npm run build проходит без ошибок ✓ Поведение в браузере идентично оригиналу ✓ Нет implicit any (tsconfig: strict: true) ✓ Файл не превышает 300 строк ✓ Каждая функция делает одно дело Правило большого пальца: если не уверен — сначала перенеси файл как есть, потом рефактори внутри. Два маленьких PR лучше одного огромного.
